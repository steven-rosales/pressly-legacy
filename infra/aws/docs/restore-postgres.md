# Restore Production Postgres

Use this only for serious data corruption or machine loss. A code rollback does
not reverse a destructive migration. The restore is a maintenance-window
operation: public ingress and every database writer remain stopped until the
replacement database passes schema, migration, ownership, and privilege checks.

## Before Restore

- Obtain owner approval and record the accepted recovery point and expected
  data-loss window.
- Choose an encrypted object whose checksum and isolated restore drill passed.
- Confirm `current-release` and `current-release.json` describe the last known
  good application identity. Normally `deployment-state.json` is verified and
  agrees. During an explicitly admitted failed migration it may instead be
  `running_unverified` or `recovering_unverified`; the script binds and
  preserves that complete unresolved identity while restoring the exact known
  application identity. It never trusts transient shell or `compose.env` image
  values.
- Record the current release manifest, database size, free disk, incident
  request IDs, and start time.
- Pause deployments and other database maintenance for the entire recovery.
- Run scheduled backups through the monitored operation wrapper so recovery and
  backup share the same `postgres-backup.lock`.
- Keep the backup passphrase and runtime database secrets available from their
  mode-`0600` files. Do not paste them into a shell history or incident note.

API and Worker are the current database-writing services. The restore script
also stops Caddy so no public request can reach API while it is being recovered.
Web, Processor, and Control are frontends, not database writers.

Provision the host authority once, outside an incident, from an independently
verified Lightsail static IP. `/etc/pressly` must be root-owned and not
group/world writable; the identity is deliberately public metadata, so the
restore user reads a root-owned mode-`0644` file without being able to replace
it.

```json
{
  "schemaVersion": 1,
  "environment": "production",
  "publicHealthTarget": {
    "hostIdentity": "pressly-production",
    "expectedPublicIpv4": "<production-static-ip>",
    "api": {
      "url": "https://api.trypressly.com/health/ready",
      "host": "api.trypressly.com"
    },
    "web": {
      "url": "https://trypressly.com/health",
      "host": "trypressly.com"
    },
    "processor": {
      "url": "https://processor.trypressly.com/health",
      "host": "processor.trypressly.com"
    },
    "control": {
      "url": "https://control.trypressly.com/health",
      "host": "control.trypressly.com"
    }
  }
}
```

Install the reviewed document without placing mutable authority in the incident
shell:

```bash
sudo install -d -o root -g root -m 0755 /etc/pressly
sudo install -o root -g root -m 0644 ./host-identity.json \
  /etc/pressly/host-identity.json
```

## Restore

1. Download and verify the encrypted object, checksum, and metadata generated by
   the same backup execution.

```bash
aws s3 cp s3://<bucket>/postgres/pressly-<timestamp>.dump.gpg /opt/pressly/backups/postgres/
aws s3 cp s3://<bucket>/postgres/pressly-<timestamp>.dump.gpg.sha256 /opt/pressly/backups/postgres/
aws s3 cp s3://<bucket>/postgres/pressly-<timestamp>.dump.gpg.json /opt/pressly/backups/postgres/
chmod 600 /opt/pressly/backups/postgres/pressly-<timestamp>.dump.gpg*
cd /opt/pressly/backups/postgres
sha256sum --check pressly-<timestamp>.dump.gpg.sha256
```

If the first release containing the stable operations bundle fails before
`ops/current` exists, use `ops/candidate/restore-postgres.sh` only when its
mode-`0600` `source-sha` exactly equals the unresolved release SHA in
`deployment-state.json`. The checksummed payload independently enforces that
relationship and refuses candidate use if any `ops/current` pointer exists. A
stale, mismatched, dangling, or general-purpose candidate fallback is rejected.

For a schema-1 or schema-2 unresolved deployment, add the explicit admission:

```bash
PRESSLY_RESTORE_ALLOW_UNVERIFIED_DEPLOYMENT=true \
PRESSLY_RESTORE_CONFIRM='pressly:pressly-<timestamp>.dump.gpg' \
  /opt/pressly/ops/current/restore-postgres.sh \
  /opt/pressly/backups/postgres/pressly-<timestamp>.dump.gpg
```

2. Run the confirmation-gated recovery workflow from the stable host operations
   bundle. Replace `pressly` if `POSTGRES_DB` has a different configured name.
   Recovery derives the static IP, exact URLs, and exact hosts only from the
   provisioned root-owned host identity. Any supplied `PRESSLY_EXPECTED_PUBLIC_IP`
   or health-URL override must match that file exactly.
   A verified deploy advances `/opt/pressly/ops/current`; an application
   rollback does not downgrade this recovery tooling. The workflow refuses lock
   contention; dirty Compose, role, or migration inputs; release pointer,
   metadata, or deployment-state disagreement; mutable image tags; wrong or
   shared GHCR repositories/digests; and image revision-label disagreement.

```bash
cd /opt/pressly/repo
PRESSLY_RESTORE_CONFIRM='pressly:pressly-<timestamp>.dump.gpg' \
  /opt/pressly/ops/current/restore-postgres.sh \
  /opt/pressly/backups/postgres/pressly-<timestamp>.dump.gpg
```

The script performs these ordered operations:

1. Verifies the encrypted checksum and metadata, exact five-image current and
   unresolved identities, clean recovery inputs, environment permissions,
   target database, local Docker context, and Compose configuration. One nonblocking
   lock excludes deploy, rollback, and another restore for the full operation;
   a second excludes Postgres backup.
2. Fsyncs the exact restore journal before starting or recreating Postgres,
   stopping a service, or changing the database. It then stops Caddy, API, and
   Worker; verifies the migration destination, revokes runtime connections, and
   terminates existing sessions.
3. Decrypts the archive into a private temporary directory and restores it into
   a newly created database. It never restores over `public` or `drizzle` in
   place.
4. Reapplies the migration, runtime, and backup roles and their grants; repairs
   the Drizzle ledger sequence; then runs every compatible migration from the
   approved API image.
5. Validates the current migration count and latest timestamp, essential
   application tables, schema/relation/function ownership, runtime reads,
   rolled-back runtime DML, backup read-only access and rejected writes, and the
   runtime role's lack of schema-create access.
6. After candidate validation, it disables connections, renames the previous
   database to a timestamped `*_damaged_*` quarantine, promotes the candidate to
   `POSTGRES_DB`, and repeats validation through the production database name.
7. Starts API and Worker with restart policies fenced to `no` and waits for both
   to become healthy. Only then does it start fenced Caddy. Immediately before
   the four pinned TLS checks and again immediately afterward, it requires every
   hostname to resolve exclusively to the journaled static IP. A schema-1
   `running_unverified` state is reconciled to the exact current application
   identity only when recovery ran from `ops/current` and every check passed.
   Candidate-origin recovery and schema-2 rollback recovery remain unresolved
   for an exact deploy or rollback retry.

Failure before journal creation proves no service or database mutation was
authorized. After fencing, all three service restart policies remain `no`
until public verification is durable. A host restart therefore cannot
automatically reopen ingress or writers. A process-only failure after the
validated services have already started can leave those containers running;
resume the exact journal promptly to finish verification or abort. The fsynced
journal records the backup basename and checksum, current and unresolved
release identities, complete unresolved deployment state, operations-bundle
origin, exact `publicHealthTarget`, target/candidate/quarantine names, restart
policy, and phase. Quarantine names include both a UTC timestamp and process
identity, and each journal phase admits only database topologies reachable from
its durable predecessor. URL, host, IP, or host-identity overrides are rejected
on resume. Re-run the exact same confirmed command after
repairing the underlying cause: a fresh process reconciles the live database
topology and resumes safely even if power failed between either database rename
and its journal update. A different backup, release, target, restart policy, or
unreachable database set is rejected while the journal is unresolved. The
script never deletes the quarantined database.

If recovery fails before either target rename, the unchanged target can be
returned to service with a second, explicit confirmation:

```bash
PRESSLY_RESTORE_CONFIRM='ABORT:pressly:pressly-<timestamp>.dump.gpg' \
  /opt/pressly/ops/<same-admitted-bundle>/restore-postgres.sh --abort-pre-cutover \
  /opt/pressly/backups/postgres/pressly-<timestamp>.dump.gpg
```

Abort is allowed only for the exact journal and backup while topology is still
target-only or candidate-ready. It validates the unchanged target, then fsyncs
the `aborting` phase and the production service-resumption decision before any
writer or ingress starts. It health-checks the exact applications and public
surfaces while retaining the candidate, removes only the recovery-owned
candidate, and finally retires the journal. A fresh process resumes safely if
power fails after that drop. Abort is categorically rejected after the target
database has been renamed. Use the same `current` or first-rollout `candidate`
bundle that created the journal. Production abort is the sole allowed restart-
policy transition: a restore journaled with service resumption disabled may
move to resumption enabled so the abort can prove application and public
health.

`PRESSLY_RESTORE_RESUME_SERVICES=false` suppresses only the final service
restart. It still replaces `POSTGRES_DB` with the restored candidate and
quarantines the previous database. Never use it as a harmless practice mode on
production; the disposable proof harness sets it only inside a unique temporary
Compose project.

## Verify And Close The Incident

As a mandatory recovery step, confirm all four public surfaces and the private
Worker after the script exits:

```bash
PRESSLY_EXPECTED_PUBLIC_IP="$(python3 - /etc/pressly/host-identity.json <<'PY'
import json
import sys
with open(sys.argv[1], encoding='utf-8') as handle:
    print(json.load(handle)['publicHealthTarget']['expectedPublicIpv4'])
PY
)"
require_2xx() {
  local hostname="$1"
  local url="$2"
  local status
  status="$(curl --silent --show-error --max-time 10 --output /dev/null \
    --write-out '%{http_code}' \
    --resolve "$hostname:443:$PRESSLY_EXPECTED_PUBLIC_IP" \
    "$url")"
  [[ "$status" == 2[0-9][0-9] ]]
}
require_2xx api.trypressly.com https://api.trypressly.com/health/ready
require_2xx trypressly.com https://trypressly.com/health
require_2xx processor.trypressly.com https://processor.trypressly.com/health
require_2xx control.trypressly.com https://control.trypressly.com/health
docker compose --env-file /opt/pressly/env/compose.env \
  -f infra/aws/lightsail/docker-compose.production.yml ps
```

Verify a bounded set of critical reads and writes through supported application
boundaries, confirm Sentry receives healthy runtime and Worker signals, and
record:

```text
approved recovery point:
actual data-loss window:
restore start and finish:
encrypted checksum:
restored release SHA:
schema and role validation: passed
public and Worker health: passed
critical application checks: passed
quarantined database:
```

Retain the quarantined database until incident review and an explicit deletion
approval. Its connections remain disabled, so ordinary services cannot use it.
Dropping it is a separate destructive action and is not part of this procedure.
The retired exact restore or abort journal remains at
`/opt/pressly/postgres-restore-last.json` as incident evidence, including the
original unresolved deployment state.

## What This Does Not Prove

The disposable proof creates a database at migration N-1, backs it up, restores
it through the current release, and requires migration N to be applied. It
proves schema-1 and both schema-2 recovery admissions, exact first-rollout
candidate binding, zero mutation before the durable journal, abort before and
after candidate creation, abort-validation failure retention, fresh-process
abort after candidate drop, rejection after target rename, and fresh-process
resume after both database renames. It exercises the same encrypted custom
archive, role/grant repair, promotion, and quarantine path without touching
production. It does not prove production
disk headroom, actual recovery time, public DNS/TLS, secret escrow, or an
operator's response during a real replacement-host incident. Those remain live
operational evidence.
